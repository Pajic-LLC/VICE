# Documentation style

VICE documentation should sound like it was written by the people building the engine.

## Rules

- Use plain human language.
- Do not use em dashes.
- Do not pad a section to make it sound more important.
- Avoid generic claims such as "revolutionary", "next generation", or "cutting edge" unless a document is quoting marketing material for review.
- Name the actual subsystem, constraint, measurement, or tradeoff.
- Separate facts, decisions, proposals, and open questions.
- Prefer short examples over abstract filler.
- State uncertainty when evidence is incomplete.
- Keep acronyms defined near their first use.

## Technical writing

A good architecture note should answer four questions:

1. What problem are we solving?
2. What are we choosing?
3. What does the choice cost us?
4. What would make us revisit it?

Do not hide tradeoffs. Future contributors need the reason behind a decision more than they need confidence theater.
