# ADR 0030: Generic quantities and atomic resource transactions

Status: Accepted for Phase 7 Slice F.

## Decision and boundaries

World owns a separate gameplay quantity-type catalog and quantity accounts keyed by `(holder persistent UUID, quantity-type UUID)`. The existing ResourceId/ResourceHandle tables remain asset references and keep their original ABI meaning. A holder is any live entity. Multiple logical containers can be separate entities connected through generic relationships; no inventory, wallet, fuel-tank, currency or military semantics are added to engine core.

A type has an immutable UUID/name/version and positive uint32 `quanta_per_unit` metadata. Arithmetic always uses integer quanta. There is no automatic conversion between types or rescaling during transfer. Amounts and capacities are nonnegative signed 64-bit integers, up to INT64_MAX; this also fits the existing structured event integer contract exactly. Negative balances/debt are game-defined state, not implicit behavior of a generic quantity account. Types are immutable while registered and registration is idempotent only for an identical definition.

Runtime account creation starts at zero. Capacity changes cannot reduce capacity below the current amount. Nonempty accounts cannot be removed, and entity destruction refuses holders with any nonzero account before changing World state. Empty accounts are removed with their entity. Production/consumption are explicit operations; transfers require distinct live holders and accounts of the same type. Failed operations distinguish invalid type/owner, missing account, insufficient quantity, capacity failure, invalid argument, storage limit and event failure.

## Atomic publication and evidence

A transaction first validates mode/amount, references, account existence, source balance and destination capacity. Bounds use subtraction/comparison before addition, preventing signed overflow. It then builds and validates a retained typed receipt using the existing causal journal. Only after successful publication does it assign the one or two integer balances; those assignments cannot fail or allocate. World is single-thread owned and emission invokes no user callbacks, so external consumers see the receipt and balances together after return. If parent validation or sequence capacity fails, balances, journal and catalogs stay unchanged. Allocation failure follows the existing engine policy.

Receipts use reserved engine schema UUID `c7000000-0000-4000-8000-000000000001`, version 1, name `vice.quantity.transaction`. Its fields are quantity-type UUID, resource version, operation (0 produce / 1 consume / 2 transfer), positive quantity, source before/after and target before/after. Production uses subject=receiving holder and zero source values; consumption uses subject=source and zero target values; transfer uses subject=source, first=target. Receipt time/origin/parents use normal World event contracts. Up to four currently retained causal parents can be supplied. An engine-owned primitive schema is not a game-defined resource meaning.

The schema is installed at type registration, before runtime transactions, avoiding catalog mutation on failed transfers. The UUID and name are reserved against conflicting schemas. Public event emission, scheduling and component attachment cannot fabricate receipt instances. The private transaction emission path is the only ordinary runtime producer. Restore validates receipt schema/version, subject/target structure and exact before/after conservation. Trusted source/save reconstruction can specify historical facts; this is consistency validation rather than cryptographic proof of past execution.

Type-use counts include accounts and retained receipts. Types cannot disappear or change while either depends on them; pruning releases historical uses. Deleted empty holders remain historical UUID references in receipts. Receipts share the existing 1024-record bounded causal history, not an unbounded financial ledger. Balances are authoritative saved World state and are never reconstructed by replaying that journal. A game requiring permanent accounting history needs a later explicit archival policy.

## Persistence and tools

Snapshot v21 adds bounded quantity-type/account tables before the existing clock tail, with v1–20 readers defaulting to empty tables. Source records are `quantity_type` and `quantity_account`. Full World snapshots/checkpoints, Editor Play clone/reset, standalone Runtime and save/load preserve type identity, quantum metadata, capacities, balances and retained receipt causes. Restore builds and validates a candidate World, rejects duplicate/stale accounts, over-capacity values, inconsistent receipts and schema conflicts, rebuilds reference counts and publishes only on complete success. Render projections omit quantity tables.

Revision-safe source edits register immutable types, explicitly seed/upsert initial accounts and remove empty accounts. Source seeding is an authoring override, not a runtime transfer or ledger replay, and intentionally does not invent gameplay history. Multi-operation edit failures do not partially publish. Runtime gameplay must use production/consumption/transfers through World or the SDK. Source editing an existing type through the registered operation rejects a conflicting version or quantum scale.

The append-only SDK exposes fixed-size copied definitions, type pages, account reads/lists, creation/capacity/removal and transactions with receipts/failure results. Existing asset-resource APIs and existing event DTO layouts remain unchanged. Write callbacks and thread checks follow the established Host API contract. Runtime/CLI inspection shows exact decimal quantities/capacities, type names/versions/quantum metadata and generic causal receipts, including historical missing entities. JSON uses strings for int64 quantities to avoid binary64 precision loss.

## Fidelity, performance and alternatives

There are no per-frame quantity updates. Stored accounts work unchanged for full, reduced or inactive regions, at large coordinates and across spatial handoff. Games or later rules explicitly decide when to produce, consume or transfer. No solver, renderer or platform type crosses the quantity API.

Limits are 4096 types, 65536 accounts and 64 resource types per holder. Ordered UUID maps provide O(log T) type lookup and O(log A) account lookup/mutation. Holder queries visit at most 64 contiguous entries; creation checks that bound without copying payloads. Type-name uniqueness checks are O(T) during registration, not simulation. Type pages return at most 64 entries. Transactions touch only their accounts, at most four parents and one bounded receipt. Reference counts avoid scanning accounts/history to remove a type. Serialization/index rebuilding scales with stored state. Stress tests report insertion/transfer cost, native record sizes and encoded snapshot size at the account limit.

Float balances were rejected because conservation and persistence should not depend on rounding. A second asset-resource interpretation was rejected because changing existing ResourceHandle meanings would break boundaries and modules. Duplicating balances in receipt logs or game modules was rejected because World owns the truth. Silent deletion/negative quantities were rejected in favor of explicit production/consumption and game policy. Arbitrary transactions over unrelated component/relationship state, multi-hop exchange/conversion, shared cross-resource capacity, permanent ledgers and networking replication are deferred. Revisit these choices only when a concrete reusable game requirement needs them; do not add genre semantics to solve that requirement.

## Inspection transport correction

Native regression under load exposed a pre-existing debug-file race: path-based file-size inspection could measure one response and then open its replacement. The reader now measures/reads one opened file handle. The publisher replaces the completed temporary file directly rather than removing the old path first. A concurrent 1000-publication/3000-read test checks complete response values. Temporary missing/open-sharing states are reported as unavailable/pending, including during Windows replacement, while malformed/oversized/incomplete data stays invalid and is not retried. Microsoft's [STL rename implementation](https://github.com/microsoft/STL/blob/main/stl/src/filesystem.cpp) uses replace-existing semantics; platform CI checks the supported toolchains. This changes no message schema or size bound. Entity-creation undo also refuses attached quantity accounts, including empty capacity state not captured by that older command.
