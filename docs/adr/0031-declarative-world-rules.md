# ADR 0031: Bounded event-triggered declarative World rules

Status: Accepted for the first Phase 7 Slice G increment.

## Decision and invariants

World owns persistent rule definitions, pending wakeups and the latest decision. Rules contain stable UUIDs, versioned declarative operation tags and copied VICE values. There is no second gameplay database, executable pointer, scripting scene graph, game genre type, agent belief store or third-party API in this contract. Native game modules use appended size-checked Host callbacks and fixed-layout copied DTOs.

Version 1 subscribes to one retained typed event schema and optionally one subject UUID. Up to eight conditions are ANDed in authored order: entity existence, a typed component-field comparison, relation existence, quantity comparison, and a World-time lower bound. Comparisons require exact matching scalar types; ordering is limited to integer/real fields and exact integer quantities. There is no implicit numeric conversion. Entity/quantity/relation/time facts are queried from the authoritative World at evaluation time. Changing a condition's input alone does not wake a rule: the game publishes its chosen typed event, or uses the scheduler to publish it later. Short-lived signals do not wake persistent rules.

One effect per rule is deliberate. Effects are whole-component upsert, retained typed event emission, quantity production/consumption/transfer, relation presence change, or one-shot event scheduling relative to evaluation time. Each uses the existing controlled World operation. Failure leaves that operation's gameplay state unchanged; the rule still consumes its wakeup and records the failure. There is no automatic retry, hidden rollback replay or whole-World copy per evaluation. Multi-effect all-or-nothing transactions are deferred until a reusable transaction/write-set design is justified. A chain of separate rules has explicit intermediate states and must not be presented as a single atomic exchange.

Emitted events and quantity receipts cite the retained trigger as a causal parent. Scheduled events persist the trigger parent through normal schedule provenance and retention rules. Component/relation effects retain their trigger and result in the latest rule decision; they do not invent a generic gameplay event or permanent audit ledger. Games choose the meaning and event granularity. Protected quantity receipts cannot be fabricated through rules.

## Wakeups, ordering, feedback and fidelity

An index maps trigger schema UUID to an ordered set of enabled rule UUIDs. Retained event publication visits only those subscribers, then checks subject filters. Each rule has at most one pending wakeup: the first event wins until evaluated, and additional matching events increment a saturating, inspectable coalesced counter. These are state-reconciliation wakeups, **not one effect for every event**. Games must use explicit native event processing for per-occurrence obligations; this first rule format does not silently promise lossless event delivery.

Pending order is `(trigger sequence, rule UUID bytes)`. A pump evaluates at most 64 rules, clamping native World budgets to that bound; the module ABI rejects invalid budgets. It captures the current causal sequence frontier before work. Events produced by effects queue new work for a subsequent pump, avoiding recursive callbacks and same-pump feedback loops. Existing pending rules evaluate live state in this deterministic order. Rule UUIDs, authored condition order and stored sequence numbers therefore matter; registration/hash iteration order does not.

World time stepping/advancement pumps schedules first, then rules, matching Editor and standalone Runtime through the common World contract. No events means no condition evaluation. An explicitly disabled rule has no subscription; disabling cancels its pending wakeup. Re-enabling does not replay old events. Rules can act on full/reduced/inactive-region stored truth without requiring a physical actor tick. A game can disable expensive distant decisions or choose coarse scheduled wakeups. Automatic paused-clock advancement does not pump; an explicit bounded dispatch remains available.

Limits: 512 stored rules, eight conditions each, one pending wakeup each, 64 evaluations per pump, 64 entries per paged query. Ordered maps/sets give O(log R) definition/pending operations; event enqueue is O(log K + M log R) for K trigger types and M matching type subscribers, bounded by 512. Dispatch is O(B(log R + C times underlying World-query cost)); it never scans all conditions every frame. Type removal performs a bounded rule-definition scan outside the simulation hot path. Debug count/page queries may scan catalog metadata. Serialization/index rebuilding scales with stored definitions/pending work. No per-entity rule instance proliferation is implied by this initial content-rule format.

## Persistence, validation and inspection

Snapshot v22 appends a bounded rule table before the clock tail and reads v1–21 with no rules. Source uses `world_rule` plus the stable text record. Operation indices in condition/effect variants are persistent tags and must only be appended; unknown versions/tags fail. Text readers bound condition counts and snapshot readers bound count/record length before allocation. Canonical ordering makes binary and source output deterministic for unchanged World state. Full snapshots, checkpoints, Play clone/reset, standalone Runtime, save/load and entity region handoff preserve the same definitions and pending/decision state; incomplete render projections omit rules and remain unsavable.

Restore builds a replacement World, restores types/entities/history/schedules/quantities, validates definitions and historical references, then rebuilds subscriber/pending indexes. Duplicate IDs, invalid schema/field/version/kind, protected payloads, malformed state or future/mismatched retained event references reject the entire restore. Restore does not execute or requeue old history. Missing entity/account endpoints can remain in dormant definitions and fail safely at evaluation. Schema/type definitions used by rules cannot be removed. A pending trigger pruned from the bounded causal journal remains a saved reference, then produces `trigger_pruned` on evaluation rather than guessing, executing or pinning unbounded history.

Native definition creation cannot inject decisions or pending references. Source edit operations `add_rule`, `remove_rule` and `set_rule_enabled` use the existing revision-safe candidate publication contract. Explicit trusted source reconstruction may contain validated historical decisions. Runtime inspection includes counts, a bounded rule page, operation/condition information, pending trigger sequence, evaluation/coalesced counters and latest applied/false/missing/pruned/rejected outcome. Module pages expose summary cursors; reading one rule exposes its full definition and decision. Outcomes explain the first failed condition by zero-based authored index. These are bounded latest explanations, not an unbounded execution trace.

## Alternatives and reasons to revisit

Full rule scans each tick were rejected for large-world scaling. Arbitrary callbacks/bytecode/Lua/Python were rejected because data-only stable operations suffice for this slice. Multi-effect best-effort lists were rejected because partial publication is easy to misread as transactional gameplay. Snapshot-copy transactions were rejected for per-rule cost. Every-event unbounded queues and permanently pinned trigger history were rejected for unbounded memory. Implicit dependency inference over every mutable engine property was deferred: explicitly typed wake events are a small inspectable starting contract.

Revisit the first-wakeup policy when a concrete game needs lossless per-event content rules, with bounded overflow/backpressure semantics and persisted payload/cursor design. Add dependency indexes, parameterized entity bindings, new condition/effect operations, transactional multi-effect write sets or richer explanations only with concrete cross-genre requirements. CRASHOUT and tactical FPS scenarios may validate these primitives; neither genre may enter core APIs.
