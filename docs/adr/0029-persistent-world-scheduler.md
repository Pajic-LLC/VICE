# ADR 0029: Persistent World-time event scheduler

Status: Accepted for Phase 7 Slice E.

## Decision

World owns scheduled event templates. Each record has a persistent UUID, absolute next-due World tick, optional recurring interval, cumulative occurrence count, explicit catch-up policy and failure state. Its event template uses the existing registered structured schema, persistent subject/target/object IDs, optional region and retained causal parents. Creation validates live references and retained parent identities before inserting anything. No callbacks, executable pointers, external gameplay database or per-entity timer loop are introduced.

Pending records are indexed by `(due_ticks, schedule UUID bytes)`. Equal deadlines therefore have a stable order independent of hash layout or restore insertion order. World-clock advancement processes at most 256 due records. Due work beyond that budget stays pending and is visible in inspection. Explicit dispatch can process another bounded batch, including while the clock is paused. Creation and restore never execute work immediately. Runtime and Editor use the same clock/dispatch path before normal game updates. Exact stepping by zero may drain already-due work; paused or disabled automatic advancement does not drain it. A zero C++ dispatch budget is a no-op; SDK dispatch explicitly requires 1–256.

A one-shot is removed after successful emission. Recurring work remains anchored to its original cadence, rather than `now + interval`. Replay fires each missed occurrence, subject to the batch budget. Coalesce fires one event for the elapsed interval range and explicitly records the represented count; the game decides what that count means. Coalescing is not an instruction to apply a financial/resource consequence once. Games needing separate consequences should use replay or explicitly interpret the aggregate count. Coalesced dispatch is ordered by the record's prior next-due key, not by its aggregate's final due time.

Firing adds `ScheduleProvenance` to the typed event data: schedule UUID, represented final due time, cumulative occurrence ordinal and represented count. The event timestamp remains the actual World time of execution, so late/backlog processing never backdates the authoritative causal journal. The UUID remains evidence after a one-shot is removed. Native gameplay cannot forge this provenance through ordinary event publication. A separate appended provenance-query function preserves the previous WorldEventSnapshot ABI layout.

## Failure and causality

A missing/deleted endpoint, invalid explicit region, exhausted event sequence or another rejected emission makes the record failed and removes it from the due index. Failed records remain saved and inspectable with a structured failure reason and original template; they do not retry every frame. Repair is explicit cancellation and new scheduling. Schema use counts include pending and failed templates until cancellation/completion. Last valid recurring emission is allowed before next-due overflow; that record then becomes failed with time overflow. Occurrence arithmetic is checked before emission and cannot wrap.

A scheduled consequence can happen long after its causes leave the bounded journal. Parents must be retained and exact at initial creation. Saved templates may subsequently hold pruned evidence, just as retained event records can. Restore checks lineage, ordering/range and exact retained UUIDs, while preserving non-nil UUIDs for pruned parents. The private scheduler emission path accepts those previously captured references; public event publication still rejects newly supplied pruned parents. This is a trusted persistence contract, not cryptographic validation of absent history. No archive or pinning policy is added.

Schedules do not keep entities alive. Deleted references survive in pending/failed intent so load can preserve the state and tools can explain the eventual failure. A coherent World restore may therefore contain pending work whose endpoint no longer exists; dispatch performs the live-reference check. Source edit creation has the same live checks as direct World creation. Signals can be scheduled, but their fired delivery records remain transient and are not replayed on load.

## Persistence and tools

Snapshot file v20 adds a bounded schedule table before the existing clock tail. Readers retain v1–19 support with an empty scheduler. Each schedule uses a bounded 8192-byte VICE structured record; source records use `world_schedule`. Scheduled event provenance is an optional `scheduled` suffix in typed event data. Full World snapshot, checkpoint, Editor Play clone/reset, standalone Runtime and save/load preserve UUIDs, template, failure, cadence, count and pending backlog. Candidate-World restore validates all records and rebuilds both indexes before publication, without firing or changing causal evidence. Failed restore leaves the current World unchanged. Render/read projections omit schedules and remain unsavable. Normal allocation failure follows the existing engine policy.

The SDK appends creation, cancellation, individual reads, bounded range pages, O(1) summary, bounded dispatch and event-provenance reads. DTOs use fixed values and existing size/thread/phase guards. Page cursors are exclusive persistent UUIDs over current state; they are not immutable snapshots across concurrent mutations. Runtime debug shows selected-entity schedule templates/failure names and their schemas, plus global queue/budget summary. CLI source inspection shows all records. Revision-safe `schedule_event` / `cancel_schedule` edits support preview and atomic publication, including endpoint/region impact reporting.

## Fidelity and cost

There is one global World clock and scheduler, including for reduced/inactive regions. No entity simulation is required to store intent or emit a fact. A missing explicit region fails; an unspecified region is resolved from the subject at execution, so spatial handoff uses current World truth. A full distributed handoff/merge protocol remains out of scope.

The UUID map and due-time set use O(log n) insertion, lookup, cancellation and per-firing reindexing. Reading the next deadline/summary is O(1); idle advancement does not scan schedules. Storage is bounded at 16384 records. Pages return at most 64. Selected-entity debug context scans the bounded table on demand and returns at most 64 with truncation; it is not a per-frame simulation path. Serialization and index rebuild scale with stored records/payload size. Stress tests print native record size, snapshot size, insertion cost and 10000 idle-step timing at capacity. Dynamic payload fields, strings, parents and tree-node overhead are additional to `sizeof(WorldSchedule)`.

A full scan each tick was rejected. A single unbounded catch-up loop was rejected because large time jumps or coarse simulation could monopolize the frame. Silently dropping missed occurrences was rejected in favor of explicit replay/coalesce semantics. Arbitrary persisted actions were rejected in favor of typed events that later rules can interpret. Timer-driven game-specific behavior, calendars, resource rules, subscribers and Agent cognition remain later layers. If measured workloads exceed the bounded tree indexes or need deadline fairness across huge replay backlogs, revisit timing wheels, per-region partitions or an explicit fairness policy without changing persistent identity or silently changing event meaning.
